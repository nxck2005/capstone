# 11. Approved addendum — checker implementation corrections

This addendum was approved with the PRE_B3 plan and is binding on §7.

## 11.1 Preserve `declared_phase()` compatibility

Do not change `declared_phase()` from its current three-value return shape while claiming existing
callers remain unaffected. Existing code and tests unpack exactly:

```python
frontier, token, done = declared_phase(body)
```

Use a separate helper for the subphase:

```python
PHASE_RE = re.compile(r"\bPB[_\- ]?(\d+)([A-D]?)\b", re.I)

def declared_subphase(body: str) -> str | None:
    frontier, _, _ = declared_phase(body)
    if frontier is None:
        return None
    match = PHASE_RE.search(frontier)
    if match is None:
        return None
    suffix = match.group(2).lower()
    return f"pb_{match.group(1)}{suffix}"
```

A structured declaration object is acceptable only if every caller and test is deliberately updated.
For PRE_B3, the separate helper is the safer change.

## 11.2 Do not classify the whole bounded-W4 parent phase as completed

The declaration says PA, PB_1 and PB_2 are complete, while PB_3 remains. Therefore
`bounded W4 integration` is a **partially completed parent phase**, not a completed alias.

The stale sentence `bounded W4 integration is the live task` must be rejected as an
**imprecise/coarse frontier nomination**, not reported as directing completed work.

The semantic rule is: when live text uses a next-action, next-phase or live-task nomination cue, it
must name the declared subphase `PB_3`. Naming only the parent milestone `W4` or the parent phrase
"bounded W4 integration" is insufficient. The finding must explain that the declared frontier is
`W4 · PB_3` but the live sentence nominates only its coarse parent.

Descriptive mentions of W4 or bounded W4 that do not claim to be the next/live task remain allowed.

## 11.3 Keep completed aliases narrowly derived

Completed aliases may include only rows explicitly declared complete — PB_1 and its correction phase,
PB_2 and PB_2C, and their corresponding instruction paths. Do not infer that every parent phrase
containing completed descendants is itself complete.

The check distinguishes four cases:

1. **Backward directive** — tells the reader to begin/run an explicitly completed phase or
   instruction.
2. **Stale nomination** — names a completed phase as next/live.
3. **Coarse nomination** — claims only W4/bounded W4 is next/live when the declaration requires PB_3.
4. **Valid frontier** — explicitly names PB_3 as next/live.

## 11.4 Historical-section handling

Reuse the existing historical logic rather than creating broader exemptions. `live_lines()` must
continue returning its existing `(line_number, line)` shape by delegating to the new
`live_lines_with_sections()` helper, which may return `(line_number, line, section_heading)`.

The existing historical rules remain authoritative: struck-through headings; headings carrying DONE,
Complete or PASS; `## Session log`; struck-through lines; existing history-record lines. Do not exempt
arbitrary prose merely because it contains words such as "historical" or "previously."

## 11.5 Mutation proof must not edit tracked `NEXT.md`

Do not temporarily modify the real repository `NEXT.md` to demonstrate that the checker fails. Prove
the rule through the synthetic unit-test fixture and/or a temporary tree used by the test helper.

The required test must assert that the checker exits 1 and that its output names the declared
frontier (`PB_3` or `W4 · PB_3`), the file, the line, the enclosing section, and the stale or coarse
phase wording.
