# C1.1 — Independently verify the suspected defect

The external audit found the following likely sequence:

1. `SionnaLDPCAdapter` constructs `LDPC5GEncoder` with `num_bits_per_symbol=q_m`.
2. Sionna applies the TS 38.212 §5.4.2.2 output interleaver after rate matching.
3. `src/baseline/classical/channel_transport.py::modulate()` applies the project `interleave()` again.
4. `demodulate()` applies the project `deinterleave()`.
5. Sionna’s decoder applies its own inverse interleaver before rate recovery.

The suspected current chain is:

```text
rate matching
→ Sionna interleaver
→ project interleaver
→ constellation mapping
→ demapping
→ project inverse interleaver
→ Sionna inverse interleaver
→ rate recovery and decoding
```

The required chain must contain exactly one modulation bit interleaver.

## Required investigation

Do not accept this claim from prose alone.

Inspect the exact installed Sionna implementation in `.venv`.

Determine and record:

* exact Sionna package version;
* exact local encoder source path;
* exact local decoder source path;
* where `num_bits_per_symbol` is stored and validated;
* whether the encoder applies the output interleaver;
* whether it occurs after rate matching;
* whether the paired decoder automatically uses the encoder’s inverse interleaver;
* whether inverse interleaving occurs before rate recovery;
* behavior for BPSK, QPSK, and 16-QAM;
* whether BPSK is an identity permutation;
* whether the project classical layer adds a second permutation.

Use local installed source as the primary evidence.

Commands and short Python probes used for the investigation must be recorded in the C1.1 Notes or worklog.

Append a technical note to:

```text
worklogs/w4-classical-baseline-progress.md
```

The note must give local source locations and the conclusion.

# Emergency protocol when usage is running out

Do not attempt one last large command.

Do not start the full test suite, a bounded execution group, or a multi-file refactor when usage appears nearly exhausted.

Perform these actions in order:

1. Stop starting new work.
2. Let the currently running command finish only if it is already close to completion; otherwise interrupt it safely.
3. Inspect:

   ```bash
   git status --short
   git diff --stat
   ```
4. Update `instructions/RESUME.md` with:

   * current C1.x row = `in-progress`;
   * exact files changed;
   * commands completed;
   * commands not run;
   * failures observed;
   * facts not yet verified;
   * the exact next command;
   * whether the worktree currently passes targeted tests.
5. If coherent work exists, commit it as:

   ```text
   wip(pb1c): preserve <precise unfinished work>
   ```
6. If code is partially broken, still commit it as WIP, but record the known failing tests and failure reason.
7. Push the commit.
8. Confirm:

   ```bash
   git rev-parse HEAD
   git rev-parse origin/main
   git ls-remote origin refs/heads/main
   ```
9. Report the durable checkpoint and stop.

Never leave a dirty, unpushed worktree as the resumption mechanism.

Never claim an `in-progress` step is complete because most of it was implemented.

Never spend the final available usage writing a polished chat report before the ledger and commit are pushed.

The emergency final response must end with:

```text
PB_1 CORRECTION INCOMPLETE — RESUME AT C1.<n>
```

and include the pushed checkpoint SHA.

If pushing is impossible because of authentication, signing, connectivity, or remote rejection:

* preserve the local commit;
* record the exact failure in `RESUME.md` if possible;
* report:

```text
PB_1 HOLD — DURABLE PUSH FAILED: <precise condition>
```
