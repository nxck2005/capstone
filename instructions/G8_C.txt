# G8_C — complete full-strength BLER characterization and freeze G-8

This instruction is the durable operational contract for G8_C. The normative
authority order is `spec/SPEC.md`, approved amendments and generated
parameters, the authenticated G8_A campaign and required identities, the
registered B1C/B2C/B3/v3 contracts, executable validators, independent

## Scope and release boundary

G8_C executes exactly the 3,213 required physical-layer BLER work units from
`results/baseline/g8/required_bler_identities.json`. Each unit uses its
authenticated `BlerIdentity`, exact SNR, packet-configuration bindings,
deterministic seed records and the registered v3 runner for exactly 5,000
trials. G8_C produces raw channel evidence, an independently reconstructed
merge report, and a separately hash-bound G-8 `BlerTable`.

G8_C may not load validation pixels, access test data, encode or decode image
codecs, reconstruct images, run classifier inference, train or fine-tune a
model, construct a `G8Authorization`, select operating points, execute either
selection pass, invoke fallback adjudication, or execute G8_D or any later
phase. The four protected counters remain zero; physical-layer
characterization is scientific execution even though it is not validation
decoding, inference, training or test access.

The G-2 BLER artifact is a narrow conformance record for one exact physical
identity and must not fill, interpolate, extrapolate or stand in for a missing
G8_C point. G8_C table construction uses measured points only. A zero-error or
all-error point is valid evidence when its integer counts and complete chain
validate.

## C1/C2 orchestration and topology

The characterization CLI validates every argument before inspecting recovery
state, opening a runner context, creating a root or launching a worker. It
accepts `--root`, `--device auto|cpu|cuda`, `--shard-count auto|positive`,
optional `--shard-index`, `--batch-size auto|positive`,
`--max-units-per-worker-batch positive`, `--repair-recoverable`,
`--plan-only`, `--reconcile-only` and `--merge-only`. The production root
must resolve exactly to `/home/nick/projects/capstone/results/baseline/g8/work_units`;
relative paths, aliases, symlinks, traversal and all alternate roots fail
closed.

Resolve `auto` only from authenticated implementation capability and hardware:
use at most one worker per supported physical GPU, otherwise one CPU worker;
never oversubscribe a GPU and never use measured BLER to choose topology.
Record resolved device, worker count, shard count, shard IDs and batch size as
execution provenance. A lower batch size is permitted only after an OOM and
must be recorded with its reason. Device and batch size never enter request
identity.

Each worker creates one authenticated runner context, authenticates authority
once, reuses it across its batch, and never shares mutable context with another
process. Before each unit, obtain a fresh B3 resume plan and reread authority.
Workers execute only assigned remaining IDs in exact required order, never a
completed or unknown ID, and stop before exclusive recoverable repair. The
coordinator alone reconciles campaign state; workers never write it.

For each unit use only the frozen transaction:

```text
clean claim → immutable request → execute from trial zero
→ immutable result → failed/result_linked terminal state
→ exact chain reread and validation
```

Every complete result is full-strength, scientific, merge-eligible, has
`trials_requested=trials_completed=5000`, exact integer information-bit/bit-
error/block-error counts, derived BER/BLER and Wilson bounds, exact seeds,
identity, SNR, implementation binding, request/result/state hashes, attempt and
shard metadata, and contribution exactly one. Failed attempts remain immutable
history and contribute zero. A process interruption or transient failed
attempt is recoverable; retry only at the next legal clean attempt, without
changing request bytes, seeds, identity, SNR, decoder, code or trial count.
Never rerun a valid terminal unit because its BLER is surprising.

At each durable batch boundary stop workers, acquire the B3 exclusive lock,
repair only its two declared recoverable classes, census raw files, reconcile
the exact newly completed IDs, validate every new chain, reject staging/lock/
partial objects, update the ledger, stage only authoritative evidence/state,
commit, push and verify parity. At most one unpushed batch may exist. The
default batch is 128 newly completed units and may be smaller for resource or
repository limits.
